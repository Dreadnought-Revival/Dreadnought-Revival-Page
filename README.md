# Dreadnought-Revival-Page

The website of the [Dreadnought Revival](https://github.com/Dreadnought-Revival) project —
a community-operated private server for the discontinued game **Dreadnought**
(unmodified game client, everything emulated server-side, one replacement launcher).

Live site: deployed with GitHub Pages from `main` (Source: GitHub Actions) →
https://dreadnought-revival.github.io/Dreadnought-Revival-Page/

## Stack

Plain static HTML/CSS/JS — no build step, no dependencies. Pages serves the repo root
(`workflow/`, the automation project below, is excluded from the published site).

```
index.html      one-page landing: hero with the Download button, three overview banners, then tabbed panels (play, status, game modes, patch notes, fleet gallery, roadmap, contribute, support)
styles.css      dark HUD theme after the original game site (Teko headings, cyan on dark teal, orange-red buttons; IBM Plex Sans/Mono for text)
app.js          ARIA tabs + hash routing, burger nav, reveal-on-scroll, status badge, patch-notes rendering, gallery lightbox
404.html        custom not-found page (same theme)
data/           patch-notes.json (player-facing notes, generated by automation), supporters.txt
                (Patreon supporters on the Support tab, edited by hand), server-status.json (optional)
assets/         Dreadnought Revival logo, favicons, BETA badge, button images, social preview
                (ship art is fetched at deploy time — see below)
workflow/       Mistral Studio workflow project (revival-patch-notes)
```

The site is a HUD-style hero followed by an ARIA tab bar (Play / Status / Game Modes /
Patch Notes / Fleet / Roadmap / Contribute / Support); URL fragments deep-link the tabs, and with
JavaScript disabled every panel stays visible. The fleet gallery shows 31 ships
grouped by class. Ship art (`assets/market-images/`) is **not in this
repo** — it is binary game data, so `deploy-pages.yml` fetches the pinned set from
the old Dreadnought-Revival-project repo at deploy time into the Pages artifact.
A fetch failure fails the Deploy Pages run visibly.

## Automation

- `.github/workflows/deploy-pages.yml` — deploys the site to GitHub Pages on every push to `main`.
- `.github/workflows/workflow-ci.yml` — runs the tests of the workflow project on every change under `workflow/`.
- Patch notes are written for players by automation — dated batches, sectioned by
  the game mode each change actually affects (game modes first, then All game
  modes, Daily contracts, Launcher / Hangar / Market / Tech tree / Social,
  General), no internals and no known-issues section — the Patch Notes tab
  links the server's GitHub issues instead. Server commits end with a
  `Patch notes:` block of player-worded lines (per the server repo's
  patch-notes skill); the workflow builds the notes from those blocks (wrapped
  block lines are joined to one bullet first), so internal commits
  (`Patch notes: none (internal)`) never reach the site, and the generation
  step validates that every block line's section made it into the batch — and
  that a line naming no known section is still recognizable in some bullet by
  its distinctive words or numbers — so a dropped line regenerates the batch
  on retry and ultimately fails the run instead of publishing incomplete
  notes. A GitHub webhook on
  [Dreadnought-Revival-server](https://github.com/Dreadnought-Revival/Dreadnought-Revival-server)
  pushes starts the `revival-patch-notes` Mistral Studio workflow, which opens a PR
  with the new notes and squash-merges it automatically once its CI is green
  (deleting the branch); if CI fails the PR stays open for the daily Vibe ops
  run (which covers launcher releases too). Never hand-edit `data/patch-notes.json`.
